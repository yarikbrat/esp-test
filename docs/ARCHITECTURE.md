# Архітектура прошивки

## Шлях даних

```
браузер ──TCP:80──► UART TO ETH (B) ──UART2 115200 8N1──► ESP32: задача bridge
                    (прозорий режим:                        парсер HTTP → API → відповідь
                     усі з'єднання в один потік,                    ▲
                     відповідь — усім з'єднанням)                   │ знімок стану під м'ютексом
                                                                    │
            задача sensors ──(м'ютекс)──► спільний стан stand_t ◄───┘
            BMP585 (I2C0), BMP581 (I2C1),       │
            HC-SR04 (GPIO + переривання)        ├──► черга persist_q ──► задача storage ──► NVS
                                                └──► задача logger ──► журнал у розділі histlog
```

**HTTP виконується на ESP32.** Модуль лише перетворює TCP на байти UART і назад, тому стандартний
`esp_http_server` (працює із сокетами) не підходить. Власний потоковий парсер HTTP/1.1 (`http_parser.c`):

- запит може прийти частинами, між запитами може бути сміття — байти, з яких не може початися метод (не A–Z),
  пропускаються (так відкидаються 32 двійкові байти, які модуль пише в UART після зміни налаштувань); якщо в
  сміття потрапили літери або переведення рядка, запит відновлюється за повним рядком запиту (`GET /`, `HEAD /`
  чи `POST /` … `HTTP/1.x`), знайденим у буфері; після
  помилки парсер сам синхронізується;
- межі: рядок запиту і заголовки до 1536 байт, тіло до 512 байт, шлях і query до 96 символів;
- тайм-аути: 2 с між байтами одного запиту, 5 с на весь запит; незавершений запит відкидається без відповіді;
- кожна відповідь має `Content-Length` і `Connection: keep-alive`: ESP32 не може закрити TCP-з'єднання, тож
  браузер має знати, де закінчується відповідь;
- сторінка — один файл (HTML, CSS і JS усередині), віддається стиснутою gzip (близько 11 КБ замість 35 КБ, близько 1 с
  на 115200 бод).

Сторінка опитує `GET /api/state` раз на секунду, тримає не більше одного запиту одночасно і не перезавантажується.
Кожен запит має `X-Req-Id` (ESP32 повертає його у відповіді) і `X-Client-Id` (ESP32 рахує сторінки, що
опитували її за останні 3 с). Так сторінка відкидає відповіді, призначені іншому клієнту, і попереджає, коли
стенд відкрито кількома клієнтами.

## Модулі коду

| Каталог / файл | Що робить | Залежності |
|---|---|---|
| `components/core/` | переносне ядро без ESP-IDF: парсер HTTP, API і JSON, модель стенда та обнулення, формула висоти, перевірка мережевих параметрів, формати NVS, кільцевий журнал, форма модуля | тільки libc; збирається і на ПК |
| `main/bmp58x.c` | драйвер BMP581/BMP585: пошук адреси, перевірка CHIP_ID, налаштування, читання, повторна ініціалізація | `esp_driver_i2c` |
| `main/sonar.c` | HC-SR04: імпульс `Trig`, фронти `Echo` у перериванні, неблокуюче вимірювання | `esp_driver_gpio`, `esp_timer` |
| `main/kv.c` | NVS: один blob на ключ | `nvs_flash` |
| `main/flash_part.c` | доступ журналу до розділу `histlog` | `esp_partition` |
| `main/app.c` | спільний стан, бекенд API, збереження нулів (задача storage) | ядро |
| `main/task_*.c` | задачі FreeRTOS | |
| `web/index.html` | сторінка, вбудовується в прошивку (і стиснута копія) | |

Ядро покрите тестами на ПК (`host/tests`, 6375 перевірок, з AddressSanitizer і UBSan), включно з детермінованим
фазингом парсера HTTP. Емулятор `host/emu` запускає ядро з потоками, що повторюють задачі прошивки.

## Задачі FreeRTOS

| Задача | Пріоритет | Період | Стек, байт (вільно під навантаженням) | Що робить |
|---|---|---|---|---|
| `bridge` | 6 | подія: байти UART, очікування до 20 мс | 6144 (близько 2800) | парсер HTTP, API, відповіді |
| `sensors` | 5 | 50 мс (`vTaskDelayUntil`), сонар кожні 100 мс | 4096 (близько 1900) | барометри 20 Гц, HC-SR04 |
| `storage` | 4 | подія: черга `persist_q` | 3072 (близько 1200) | запис нулів у NVS |
| `logger` | 3 | інтервал журналу (1–3600 с) або сповіщення | 4096 (близько 3100) | запис історії, очищення журналу |
| `button` | 2 | 50 мс; звіт пам'яті раз на хвилину | 3072 (близько 1000) | кнопка BOOT, звіт `health` |

Обґрунтування:

- **bridge** найвищий: від нього залежить, чи отримає браузер відповідь вчасно. Більшу частину часу він чекає
  на UART і не займає процесор. Стек найбільший: API тримає на стеку до 20 записів журналу (640 байт) і знімок стану.
- **sensors** нижче за bridge, але вище за роботу з flash: період 50 мс не повинен зриватися через запис журналу.
  Читання I2C коротке (обмін 6 байтами); HC-SR04 не блокує задачу: фронти `Echo` фіксує переривання, результат
  забирається на наступному циклі.
- **storage** і **logger** працюють із flash і можуть чекати десятки мілісекунд (стирання сектора), тому вони
  нижче за обмін і вимірювання.
- **button** найнижча: людина тримає кнопку секунди.
- Усі очікування звільняють процесор: `uart_read_bytes` із тайм-аутом, `vTaskDelayUntil`, `xQueueReceive`,
  `ulTaskNotifyTake`, `vTaskDelay`.
- Стеки підібрано із запасом і перевірено звітом `health` (`uxTaskGetStackHighWaterMark`). Динамічного виділення
  пам'яті немає; вільна купа під навантаженням не змінюється (255 572 байт).

## Синхронізація

- **`g_app.lock`** (м'ютекс) захищає спільний стан: модель стенда, налаштування, лічильники. Будь-яка зміна
  `stand_t` іде під ним. Вебчастина бере знімок стану під м'ютексом і далі працює з копією, тож формування JSON
  не тримає м'ютекс.
- **`g_app.log_lock`** захищає об'єкт журналу: стирання сектора триває десятки мілісекунд, і основний м'ютекс
  весь цей час не тримається. Порядок: спочатку `log_lock`, потім `lock`; чекати `log_lock`, тримаючи `lock`,
  заборонено. Лічильники журналу задача logger копіює в спільний стан після кожної операції.
- **Черга `persist_q`**: задача sensors повідомляє «нуль каналу N готовий», задача storage пише його в NVS
  поза м'ютексом. Storage — єдиний записувач нулів і бере значення з RAM у момент запису, тому пізнє скидання
  нуля ніколи не перезапишеться старим результатом калібрування.
- **Сповіщення задачі logger** (`xTaskNotifyGive`): нові налаштування журналу або запит на очищення.
- **Обнулення і вимірювання** синхронізовані через той самий м'ютекс: старт калібрування, кожне вимірювання і
  завершення калібрування — під `lock`; повторне натискання під час калібрування відхиляється
  («Калібрування вже виконується»).

## Обробка помилок

| Ситуація | Що відбувається |
|---|---|
| Немає ACK від барометра, неправильний CHIP_ID | статус «Датчик не відповідає», спроба ініціалізації раз на секунду |
| 3 помилки читання поспіль | повторна ініціалізація датчика (скидання шини I2C, програмне скидання BMP58x) |
| Тиск поза 30–125 кПа | статус «Значення поза діапазоном», значення не використовується |
| Немає `Echo`, `Echo` задовгий або завис у 1 | статус «Немає сигналу ECHO» або «поза діапазоном» |
| Дані старіші за 1 с (барометр) або 0.5 с (сонар) | сторінка показує останнє значення з позначкою «застаріле», висота не рахується |
| Помилка запису NVS | нуль або налаштування діють у RAM, сторінка показує «не збережено у пам'ять» |
| Помилка запису журналу | лічильник помилок запису і код на сторінці |
| Пошкоджений запис NVS | значення за замовчуванням, сторінка показує джерело налаштувань |
| Пошкоджений запит HTTP | 400/413/414/431/501 без зависання, парсер синхронізується |
| Розрив Ethernet | ESP32 не бачить TCP-з'єднань, тож нічого не перезапускається; незавершений запит відкидається за тайм-аутом, після відновлення кабелю сторінка повторює запити (перевірено на стенді) |

Помилка одного каналу не блокує інші: кожен датчик має свій статус, кожне звернення до I2C обмежене 20 мс.
Спроба повторної ініціалізації (близько 0.1 с раз на секунду) лише ненадовго затримує опитування інших датчиків.
Діагностика в лог UART0: повідомлення запуску, по одному рядку на подію помилки, звіт пам'яті раз на хвилину,
без безперервного засмічення.

## Розрахунок висоти

Δh = 44330 × (1 − (p / p₀)^0.1903) м (`components/core/src/altitude.c`), p і p₀ у Па.

- p = p₀ → 0; p < p₀ → «+»; p > p₀ → «−».
- p — ковзне середнє останніх 20 вимірювань (1 с); p₀ — середнє щонайменше 10 сирих вимірювань за 1–3 с.
- До першого обнулення висота не визначена («Нуль не встановлено»), невалідні дані ніколи не замінюються числом 0.

## Збереження даних

### NVS (простір `stand`)

| Ключ | Розмір | Вміст |
|---|---|---|
| `net` | 20 Б | активні IP, маска, шлюз |
| `netp` | 20 Б | очікувані IP, маска, шлюз: надіслані модулю, ще не підтверджені за новою адресою |
| `zero0`, `zero1` | 16 Б | ознака встановленого нуля і p₀ для BMP585 і BMP581 окремо |
| `log` | 12 Б | журналювання увімкнено/вимкнено, інтервал |
| `boot` | 2 Б | лічильник запусків = номер сесії в журналі |

Формат blob: magic (2 Б), версія (1 Б), аргумент (номер каналу для нулів), дані, CRC32. Розмір, magic, версія,
канал, CRC і діапазони значень перевіряються під час читання; будь-яка розбіжність → значення за замовчуванням і
позначка «пошкоджено» на сторінці. Окремий blob на кожен барометр: обнулення одного каналу не торкається іншого.

Моменти запису: після успішного обнулення, після скидання нуля, після збереження налаштувань журналу, після
прийнятих нових мережевих параметрів (`netp`) і їх підтвердження за новою адресою (`net`), при старті
(лічильник сесій), при утриманні BOOT. NVS сама вирівнює зношування.

### Журнал історії

- Розділ `histlog`: 256 КБ, 64 сектори по 4 КБ, запис 32 Б: номер, сесія, прапорці валідності/нуля/статусу
  для кожного каналу, секунди від початку сесії, тиск і висота обох каналів, CRC32.
- Запис номер `seq` лежить у слоті `seq % 8192`. Сектор стирається, коли пишеться його перший слот, тобто один
  раз за повне коло: зношування рівномірне, кількість стирань — одне на 128 записів.
- Запис пишеться у flash одразу і перевіряється зворотним читанням. Буфера в RAM немає, бо запис у стертий flash
  не зношує його. При раптовому вимкненні втрачається щонайбільше запис, що саме пишеться; недописаний слот
  при наступному старті не проходить перевірку CRC і пропускається.
- Під час старту журнал сканується, знаходиться найновіший запис; записи попередніх сесій доступні на сторінці.
- Очищення не стирає розділ, а дописує запис-позначку: усе, що старіше за неї, вважається видаленим і
  перезаписується звичайним колом. Під час стирання сектора flash ESP32 зупиняє код і переривання, що працюють
  із flash, тож стирання всіх 64 секторів поспіль (близько 3 с) зупиняло б вимірювання HC-SR04. Позначка
  переживає перезапуск; номери записів після очищення продовжуються. Прошивки, старші за цю зміну, позначку не знають:
  після повернення до них очищені записи знову з'являться.
- Обидва канали беруться з одного знімка стану, тож належать одному циклу журналювання. Відмова одного каналу
  записується як його статус, а валідні дані іншого зберігаються.
- Інтервал журналу не впливає на частоту опитування датчиків і оновлення сторінки: це окрема задача.
