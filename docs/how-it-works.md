# Как устроен код стенда: объяснение для защиты

Рабочий документ для владельца проекта, без знания C. Официальное описание на украинском: `README.md` и
`docs/ARCHITECTURE.md`; этот файл объясняет то же самое простыми словами и готовит к вопросам из раздела 11 ТЗ.

## 1. На чём написано

| Часть | Язык | Где |
|---|---|---|
| Прошивка ESP32 | **C** (стандарт C11) | `main/`, `components/core/` |
| Веб-страница | HTML, CSS, JavaScript в одном файле | `web/index.html`, вшивается в прошивку |
| Тесты и эмулятор на ПК | C | `host/` |
| Сборка | CMake (через `idf.py`) | `CMakeLists.txt` |

**ESP-IDF** — официальный набор инструментов от Espressif, производителя ESP32 (версия 5.5.6). Это не
«библиотека», а основа: компилятор, система сборки, программа прошивки и стандартные модули. Из него мы берём:

| Модуль ESP-IDF | Для чего |
|---|---|
| **FreeRTOS** | многозадачность: несколько задач работают «одновременно» |
| `esp_driver_uart` | обмен с модулем Ethernet по UART |
| `esp_driver_i2c` | шина I2C к барометрам |
| `esp_driver_gpio` | выводы: импульс `Trig`, прерывание на `Echo`, кнопка BOOT |
| `esp_timer` | точное время в микросекундах (замер эха) |
| `nvs_flash` | NVS: хранилище настроек во flash |
| `esp_partition` | доступ к разделу flash под журнал |

**Сторонних библиотек нет.** Драйверы датчиков, HTTP-сервер, JSON, журнал написаны в проекте. Почему не взяли
готовый HTTP-сервер ESP-IDF: он работает с сетью, а у ESP32 в стенде сети нет, только провод UART до модуля.
Регистры BMP585/BMP581 взяты из документации и официального драйвера Bosch (BMP5_SensorAPI).

## 2. Как устроен стенд в целом

```
браузер ──кабель Ethernet──► модуль UART TO ETH (B) ──провод UART──► ESP32 ──I2C──► BMP585, BMP581
                                                                           └──GPIO──► HC-SR04
```

- **Модуль Ethernet** «тупой»: принимает байты из сети и отдаёт их в провод UART, и обратно. Он не понимает
  HTTP. Всю работу веб-сервера делает ESP32.
- **ESP32** опрашивает датчики, считает высоту, хранит настройки и отвечает браузеру.
- **Страница** сама раз в секунду спрашивает у стенда свежие данные (`/api/state`) и перерисовывает цифры без
  перезагрузки.

## 3. Карта кода

Читать удобно начиная с `main/main.c`: там видно, что запускается и в каком порядке.

**`main/`: всё, что зависит от железа ESP32**

| Файл | Что делает |
|---|---|
| `main.c` | точка входа `app_main`: загружает настройки, открывает журнал, создаёт 5 задач |
| `board.h` | какой провод на каком выводе (карта выводов) |
| `app.c`, `app.h` | общее состояние стенда и функции, которые вызывает веб-часть (обнулить, сохранить…) |
| `bmp58x.c` | драйвер барометров: найти, проверить `CHIP_ID`, настроить, читать |
| `sonar.c` | драйвер HC-SR04: импульс `Trig`, фронты `Echo` ловит прерывание |
| `kv.c` | запись и чтение настроек в NVS |
| `flash_part.c` | чтение, запись, стирание раздела журнала |
| `task_sensors.c` | задача опроса датчиков |
| `task_bridge.c` | задача обмена с модулем: принять запрос, ответить |
| `task_logger.c` | задача журнала |
| `task_button.c` | задача кнопки BOOT и отчёта о памяти |

**`components/core/`: «чистая» логика без железа.** Собирается и на ESP32, и на ПК, поэтому её проверяют
тесты (`make -C host test`, 6386 проверок).

| Файл | Что делает |
|---|---|
| `http_parser.c` | разбирает HTTP-запрос, который приходит по кускам |
| `api.c` | маршруты `/api/state`, `/api/zero`, `/api/log`, `/api/net` …; собирает ответы JSON |
| `jsonw.c` | формирует JSON |
| `stand.c` | модель стенда: статусы датчиков, усреднение, запись в журнал |
| `zero_cal.c` | обнуление (калибровка нуля) |
| `altitude.c` | формула высоты |
| `netcfg.c` | проверка IP, маски, шлюза |
| `settings_codec.c` | формат записей NVS с проверкой (CRC) |
| `histlog.c` | кольцевой журнал во flash |
| `uart_eth.c` | форма настроек модуля Ethernet |
| `form.c` | разбор полей формы из запроса (`ip=…&mask=…`) |
| `crc32.c` | контрольная сумма CRC32 для записей NVS и журнала |

## 4. Задачи FreeRTOS

**Задача** — отдельная «программа», у которой свой бесконечный цикл. FreeRTOS переключает задачи по таймеру
1000 раз в секунду (`CONFIG_FREERTOS_HZ=1000`) и сразу, когда задача чего-то ждёт. **Приоритет** решает, кто получит процессор первым, если готовы несколько.

| Задача | Приоритет | Как часто | Что делает |
|---|---|---|---|
| `bridge` | 6 (выше всех) | когда пришли байты | отвечает браузеру |
| `sensors` | 5 | каждые 50 мс (20 раз в секунду) | барометры; дальномер каждые 100 мс |
| `storage` | 4 | по сообщению из очереди | записывает нули в NVS |
| `logger` | 3 | раз в интервал журнала | пишет запись истории во flash |
| `button` | 2 (ниже всех) | каждые 50 мс | кнопка BOOT, отчёт о памяти раз в минуту |

Почему так: ответ браузеру важнее всего, иначе страница «зависает»; опрос датчиков не должен сбиваться;
запись во flash медленная (стирание блока 4 КБ — десятки миллисекунд), поэтому её задачи ниже; кнопку человек держит секунды.

**Как задачи делятся данными.** Общее состояние (`g_app`) защищено **мьютексом** — «замком»: кто взял замок,
тот читает или меняет данные, остальные ждут. Веб-часть берёт под замком копию состояния и строит ответ уже из
копии, чтобы не держать замок долго. Нули передаются в задачу `storage` через **очередь** (почтовый ящик между
задачами).

## 5. Как работают главные функции

**Барометры.** Режим normal, 25 измерений в секунду, усреднение внутри датчика ×8 по давлению. ESP32 читает
их 20 раз в секунду и берёт скользящее среднее за 1 секунду (20 значений): шум упал с ~9 см до ~4 см.

**Обнуление.** Кнопка «Встановити нуль» собирает не меньше 10 сырых измерений за 1–3 с; их среднее становится
опорным давлением p₀. p₀ сохраняется в NVS отдельно для каждого барометра.

**Высота.** Δh = 44330 × (1 − (p / p₀)^0.1903) метров. Давление ниже p₀ → «+» (поднялись), выше → «−».

**Дальномер.** ESP32 даёт импульс 10 мкс на `Trig`. Датчик отвечает на `Echo` импульсом, длина которого равна
времени полёта звука туда и обратно. Начало и конец импульса ловит прерывание с точным временем. Расстояние =
время × 343 м/с ÷ 2. Показывается медиана 5 последних замеров (отбрасывает одиночные выбросы).

**Журнал.** Кольцо из 8192 записей по 32 байта в разделе flash 256 КБ (64 блока по 4 КБ, 128 записей в блоке).
Новая запись идёт в следующую ячейку. Когда кольцо заполнено, стирается самый старый блок целиком, сразу 128
записей, поэтому гарантированно хранятся не меньше 8064 последних записей. Каждый блок стирается один раз за
круг, поэтому износ равномерный.
Запись пишется сразу, при внезапном отключении теряется максимум одна запись. Очистка не стирает раздел, а
дописывает запись-метку «всё старше меня удалено».

**Настройки (NVS).** IP, нули каждого барометра, настройки журнала, счётчик запусков. У каждой записи есть
контрольная сумма: если запись повреждена, берётся значение по умолчанию и страница это показывает.

## 6. Ответы на вопросы из раздела 11 ТЗ

**Выбор GPIO и уровни сигналов.**
Все сигналы ESP32 — 3.3 В. Барометры питаются от 3.3 В. Модуль Ethernet питается от 5 В (вывод `VIN`, чтобы
не нагружать стабилизатор ESP32), но его сигналы `TXD`/`RXD` — 3.3 В, поэтому они подключены к ESP32 напрямую.
HC-SR04 питается от 5 В и отвечает 5 В на `Echo`, а вход ESP32 выдерживает до 3.6 В, поэтому стоит делитель
1 кОм / 2 кОм: 5 × 2 / 3 ≈ 3.3 В (по расчёту; мультиметром на стенде не измерялось, см. `docs/connections.md`).
`Trig` от ESP32 3.3 В датчику хватает. Выводы выбраны так, чтобы не трогать «особые»: GPIO 2, 5, 12, 15 влияют
на режим загрузки (strapping), GPIO 6–11 заняты flash-памятью, GPIO 34–39 только на вход. Исключение — GPIO0:
это и есть кнопка BOOT на плате, прошивка только читает его как вход уже после загрузки, это безопасно.
UART2 на GPIO16/17 и I2C на 21/22 — стандартные выводы платы.

**Как избежали конфликта I2C.**
У BMP585 и BMP581 одинаковый адрес 0x47. На одной шине они бы мешали друг другу. Поэтому две отдельные шины:
I2C0 (GPIO21/22) для BMP585 и I2C1 (GPIO18/19) для BMP581. Плюс: зависший датчик не может «занять» шину второго.
Прошивка проверяет `CHIP_ID` (0x51 у BMP585, 0x50 у BMP581) и заметит, если датчики перепутать.

**Путь HTTP-запроса.**
Браузер → TCP на порт 80 модуля → модуль шлёт байты по UART (115200 бод) → задача `bridge` в ESP32 читает их
→ `http_parser` собирает запрос → `api.c` выбирает обработчик → ответ JSON → обратно по UART → модуль → TCP →
браузер. Страница хранится в прошивке сжатой (около 11 КБ вместо 35 КБ, около 1 с по UART), иначе грузилась бы
втрое дольше.

**Давление, абсолютная и относительная высота.**
Давление — то, что меряет датчик (Па, гПа). Абсолютная высота — над уровнем моря: для неё нужно знать давление
на уровне моря сейчас, а оно меняется с погодой, поэтому точно её не посчитать. Относительная высота — разница
с точкой, где нажали «нуль»: давление p₀ измерено здесь же, поэтому разница получается точной. Её мы и
показываем.

**Причины дрейфа показаний.**
Главная — погода: атмосферное давление меняется на ~1 гПа за час, это ~8 м «высоты». Ещё сквозняки и
кондиционер (меняют давление на десятки Па), нагрев датчика, разница между датчиками. Поэтому перед замером
подъёма обнуляют оба датчика и поднимают сразу. На стенде за несколько часов набежало +4…+6 м — это норма.

**Поведение при частичном UART-пакете.**
Запрос может прийти кусками. Парсер копит байты, пока запрос не соберётся. Если между байтами пауза больше 2 с
или весь запрос дольше 5 с, незаконченный запрос отбрасывается, стенд работает дальше. Слишком длинные
запросы получают ошибку 413/414/431. Мусор между запросами пропускается: например, 32 служебных байта, которые
модуль сам пишет в UART после смены настроек.

**Отказ датчика.**
У каждого канала свой статус. Если датчик не отвечает, на странице «Датчик не відповідає», ESP32 пробует
переподключить его раз в секунду. После 3 ошибок чтения подряд — сброс шины и датчика. Все датчики опрашивает
одна задача по очереди, и каждое обращение к I2C ограничено 20 мс, поэтому отказ одного датчика не
останавливает остальные. Попытка переподключения длится около 0.1 с раз в секунду: в этот момент опрос
остальных датчиков ненадолго задерживается, но не прерывается. Старые значения помечаются «застаріле», вместо
неверных данных никогда не показывается 0.

**Деление на задачи и приоритеты** — раздел 4 выше.

**Защита общих данных.** Мьютекс `g_app.lock` на общее состояние; отдельный мьютекс `log_lock` на журнал, чтобы
стирание блока flash не задерживало остальных; очередь `persist_q` для записи нулей.

**Возможные причины взаимной блокировки (deadlock) и как их избежали.**
Deadlock — две задачи ждут друг друга вечно: первая держит замок A и ждёт B, вторая держит B и ждёт A.
Защита: замки всегда берутся в одном порядке (сначала `log_lock`, потом `lock`), и ждать `log_lock`, держа
`lock`, запрещено. Долгие действия (запись во flash, формирование ответа) делаются без замка, по копии данных.
Мьютексы FreeRTOS поднимают приоритет держателю замка (наследование приоритета), чтобы низкоприоритетная задача
не задерживала высокоприоритетную.

## 7. Словарь

| Слово | Значение |
|---|---|
| GPIO | вывод микроконтроллера, которым программа управляет |
| UART | последовательный порт: два провода, передача и приём |
| I2C | шина из двух проводов (данные SDA и такт SCL) для датчиков |
| Прерывание | мгновенная реакция на событие на выводе, в обход обычных задач |
| Flash | энергонезависимая память ESP32 (4 МБ): прошивка, настройки, журнал |
| NVS | часть flash для настроек «ключ → значение» |
| Мьютекс | «замок», чтобы две задачи не меняли данные одновременно |
| Очередь | «почтовый ящик» между задачами |
| JSON | текстовый формат данных, в нём стенд отвечает странице |
| CRC | контрольная сумма: показывает, что запись не повреждена |
