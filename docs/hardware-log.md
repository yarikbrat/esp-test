### Плата ESP32

### Как подключить плату к WSL (повторять на каждой машине)
1. Установить usbipd-win (Windows, один раз): `winget install --id dorssel.usbipd-win -e`.
2. Найти плату: `usbipd list` (строка `USB-SERIAL CH340`, запомнить BUSID, на ноутбуке был `3-1`).
3. Разрешить проброс (один раз, от администратора): `usbipd bind --busid <BUSID>`.
4. Пробросить в WSL (после каждого переподключения кабеля или перезагрузки): `usbipd attach --wsl --busid <BUSID>`.
   В WSL появится `/dev/ttyUSB0`, а COM-порт в Windows пропадёт.
5. Права на порт: добавить пользователя в группу `dialout`. Без пароля sudo это делается из WSL так:
   `wsl.exe -d <дистрибутив> -u root -- usermod -aG dialout <пользователь>`; до перезахода в WSL временно
   `wsl.exe -d <дистрибутив> -u root -- chmod a+rw /dev/ttyUSB0`.

### Команды

- Разбор «чужих байтов»: один клиент — 400 запросов подряд (каждый в новом TCP-соединении, в том числе при записи
  истории раз в секунду), 0 ошибок. Клиент с keep-alive плюс второй клиент одновременно — ошибки у обоих
  (6 из 16 и 3 из 60): модуль рассылает каждый ответ во все открытые соединения, и клиент получает ответ на
  чужой запрос. Значит, прежние сбои были, когда параллельно со мной была открыта страница в браузере.
- Защита на странице: каждый запрос несёт заголовок `X-Req-Id`, ESP32 возвращает его в ответе (только буквы и
  цифры, до 16 символов). Если номер чужой, ответ отбрасывается, а страница показывает предупреждение «Стенд
  відкрито ще в іншій вкладці…». Проверено в эмуляторе (браузер плюс второй клиент: предупреждение появилось,
  связь не потерялась) и на стенде (эхо `X-Req-Id` есть, мусорный заголовок не возвращается). Две вкладки одного
  браузера обычно делят одно соединение и не мешают друг другу.
- Прошивка пишет в лог начало отброшенного или незавершённого запроса (одна строка), для диагностики.
- Замечание пользователя (две вкладки в разных браузерах): предупреждение было только в новой вкладке и пропадало;
  во второй вкладке после калибровки «висело» «Калібрування…». Исправлено: каждая страница шлёт `X-Client-Id`,
  ESP32 считает страницы, опрашивавшие её за последние 3 с, и отдаёт число в `/api/state` (`clients`),
  предупреждение показывают все страницы, пока их больше одной; любая страница, увидевшая идущую калибровку,
  показывает её итог. Проверено в эмуляторе: две вкладки, `clients: 2`, предупреждение в обеих, итог калибровки
  в обеих, после закрытия одной вкладки предупреждение исчезает через 3 с.
- При открытии второй вкладки, пока первая опрашивает стенд, вторая может получить вместо страницы чужой ответ
  (JSON). Это та же рассылка ответов модулем; помогает обновление страницы (F5). Записать в ограничения README.
- VirCom (`VirCom_en.exe`) находит модуль поиском (компьютер в той же подсети 192.168.144.x).
- По итогам `/code-review` смена адреса переделана: обычный запрос на новый адрес больше не фиксирует настройки
  (иначе при смене только маски их фиксировал бы первый же опрос, ещё до формы модуля, и была гонка двух смен
  подряд). Фиксирует только `POST /api/net/commit`, пришедший на ожидающий адрес; ожидающие настройки лежат
  в NVS (`netp`) и переживают перезагрузку. Модулю форма шлётся на адрес, по которому открыта страница.
- Новая находка: после применения настроек модуль сам пишет в UART 32 двоичных байта (`00 ff 00 ff 00 00 00 fe
  00 fe 00 00 ff 00 00 40 ff 00 00 a0 fd 01 00 00 08 a9 ff 02 00 00 00 00`). Парсер склеивал их со следующим
  запросом и отвечал 501. Теперь между запросами парсер пропускает всё, что не может начинать метод (не A–Z):
