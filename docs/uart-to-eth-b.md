# UART TO ETH (B): что известно до прихода железа

Модуль Waveshare построен на ядре ZLAN (утилита Vircom, протокол Realcom). Мануал ZLSN3003S подтверждает родство.

## Заводские настройки
- Заводские настройки (проверено сбросом через `DEF` 2026-10-24, прошивка V1.452, MAC 28-80-E4-96-1E-BE): IP **192.168.1.254**, порт данных 80, веб на 80, пароль пустой, маска 255.255.255.0, шлюз 192.168.1.1. Модуль пришёл с адресом 192.168.1.200 и портом данных 4196: это была чья-то прежняя настройка.
- Пин DEF к GND дольше 1 с возвращает заводские настройки.
- Встроенный веб-конфигуратор слушает порт 80. Порт меняется полем «Device Web Port».
- TCP Server держит до 30 соединений одновременно; ограничения числа соединений в веб-форме нет.

## Способы менять IP модуля из стенда

| Вариант | Как | Статус |
|---|---|---|
| A. Последовательные команды | ESP32 шлёт команду в UART. По мануалу ZLSN3003S у команд 10-байтовый преамбульный код, переключать режим не нужно. Формат описан в отдельном документе ZLAN «串口修改参数及硬件TCPIP协议栈». | Документ публично не найден. |
| B. Веб-конфигуратор модуля из браузера | Страница стенда после подтверждения отправляет форму на `http://<ip>:<web port>/ok.html` с полным набором полей. ESP32 хранит копию всех параметров модуля в NVS, чтобы форма была полной. | Поля известны (ниже). Проверить на железе, нужен ли перед этим логин. |
| C. Вручную через Vircom | Смена IP в Vircom плюс отдельная запись в ESP32. | Запасной вариант, тогда это ограничение надо явно указать в README. |

## Форма веб-конфигуратора (из `Waveshare_web_uart_to_eth_b.zip`)

Источник: https://www.waveshare.com/w/upload/a/aa/Waveshare_web_uart_to_eth_b.zip

- **Логин:** `POST /ip_en.html`, поле `lgk` (пароль, по умолчанию пустой; в комментарии страницы упомянут `admin`).
- **Сохранение:** `POST /ok.html`, отправляются все поля формы.

| Поле | Значение | Варианты |
|---|---|---|
| `dvn` | имя устройства, до 9 символов | |
| `lca` | IP | |
| `lcp` | порт TCP | для стенда 80 |
| `wbp` | порт веб-конфигуратора | для стенда 8000 |
| `lcm` | маска | |
| `lcg` | шлюз | |
| `wkm` | режим | 0 TCP Server, 1 TCP Client, 2 UDP, 3 UDP Group |
| `ipm` | IP-режим | 0 Static, 1 DHCP |
| `bdr` | скорость | 0 1200 … 9 57600, A 76800, B 115200 |
| `dtb` | биты данных | 0 = 8, 1 = 7, 2 = 6, 3 = 5 |
| `prt` | чётность | 0 None, 1 Odd, 2 Even, 3 Mark, 4 Space |
| `stb` | стоп-биты | 0 = 1, 1 = 2 |
| `flc` | управление потоком | 0 None, 1 CTS/RTS, 2 DSR/DTR, 3 XON/XOFF |
| `dsa`, `dsp` | адрес и порт назначения | для режима клиента |
| `ndr`, `nrt` | перезапуск без данных: вкл/выкл и время | **держать выключенным**, иначе модуль сам перезагрузится, если долго нет запросов |
| `rct` | время переподключения | |

| `rcg` | интервал конфликта RS485 | |
| `nwk`, `rtp` | новый пароль и повтор | |

Целевые настройки стенда: TCP Server, порт 80, веб-конфигуратор на 8000, Static, 192.168.144.36/24, 115200 8N1, без управления потоком, протокол None, перезапуск без данных выключен.

## Проверить первым делом на железе
1. Поведение при двух клиентах одновременно: смешиваются ли запросы, кому уходит ответ (`host/emu_check.py` на реальном IP).
2. Работает ли `POST /ok.html` без предварительного логина, и с какого адреса (вариант B).
3. Пины LINK и LINK2: уровни при подключении и отключении кабеля и TCP-соединения.
4. Реальная максимальная скорость UART (в таблице до 460800, на wiki до 115200).

## Проверено на железе 2026-10-24

- Найти модуль с неизвестным адресом: дать сетевому порту ПК адрес в нужной сети, пропинговать все адреса
  (`for /L %i in (1,1,254) do @start /b ping -n 1 -w 300 192.168.1.%i >nul`) и посмотреть `arp -a`.
  Модуль узнаётся по MAC `28-80-e4-...`.
- Вход в веб-конфигуратор: `POST /ip_en.html` с `lgk=` (пустой пароль). Cookie нет, сессия держится на стороне модуля.
- Сохранение: `POST /ok.html` со всеми полями формы. Модуль отвечает «Success!» и ссылкой на новый адрес.
  Если настройки приняты, модуль сразу начинает отвечать по новому адресу, перезапуск не нужен.
- Пока на `DEF` держится 0, модуль отвечает «Success!», но настройки не сохраняет (и сбрасывается к заводским).
- **Ловушка (проверено экспериментом 2026-10-24):** если новый порт данных (`lcp`) равен **текущему** порту
  веб-конфигуратора (`wbp`), модуль отвечает «Success!», но не сохраняет ничего, ни одного поля.

  | Было (`lcp`/`wbp`) | Отправили (`lcp`/`wbp`) | Кто | Результат |
  |---|---|---|---|
  | 4196 / 80 | 80 / 8000 | curl, через несколько минут после входа | не сохранилось |
  | 4196 / 80 | 80 / 8000 | браузер | не сохранилось |
  | 4196 / 80 | 4196 / 8000 | curl | сохранилось сразу |
  | 4196 / 8000 | 80 / 8000 | curl | сохранилось сразу |
  | 80 / 8000 | 4196 / 80 | браузер, в один шаг | сохранилось сразу |
  | 4196 / 80 | 80 / 8000 | браузер, в течение минуты после входа | не сохранилось |
  | 4196 / 80 | 80 / 8000 | curl, сразу после входа | не сохранилось |
  | 4196 / 80 | 81 / 8000 | curl, сразу после входа | сохранилось сразу |

  Время после входа ни при чём, остальные поля тоже. Обратный случай (новый `wbp` равен текущему `lcp`) работает.
  Рабочий порядок из заводских настроек: сначала `wbp=8000` (можно вместе с адресом), потом отдельной формой `lcp=80`.
  Для прошивки стенда: если когда-нибудь менять порт данных, учитывать это правило.
- Настройки применяются сразу, без перезапуска, и переживают выключение питания (проверено).
- Текущие настройки: 192.168.144.36/24, шлюз 192.168.144.1, TCP Server, порт данных 80, веб-конфигуратор на 8000,
  115200 8N1, без управления потоком, No-Data-Restart выключен, протокол None.
- Вариант B (смена адреса модуля формой из браузера) работает, если перед формой был вход (вход тоже делает страница).
  Реализован в прошивке и странице: `POST /api/net` возвращает `module_url` и готовую форму `module_form`
  (`components/core/src/uart_eth.c`), страница шлёт её модулю (`fetch` с `mode: "no-cors"`), ESP32 делает
  настройки активными при первом запросе с `Host` = новый адрес. Пустой шлюз модуль принимает как `0.0.0.0`.
- **Два клиента:** запросы всех TCP-соединений приходят в UART одним потоком, а каждый ответ ESP32 модуль
  рассылает во все открытые соединения. Проверено двумя одновременными `curl.exe`: оба получили один и тот же
  ответ. Стенд должен считать, что ответ может прочитать «не тот» клиент (см. `PLAN.md` §3).
- Две вкладки одного браузера обычно работают через одно соединение и друг другу не мешают. Разные браузеры или
  компьютеры одновременно получают ответы друг друга. Страница распознаёт это по `X-Req-Id` и предупреждает.
